# Arashi Works 网站实施方案


> 中文品牌：山嵐异造坊
> 仓库名称：arashi-works-web
> 文档状态：实施基线，已完成实施前审查
> 当前阶段：阶段B——本地基础工程，不部署

## 1. 项目定位

Arashi Works 是山嵐的个人创作网站，用于集中展示和记录：

- 小型软件与实用工具。
- 实验性程序和技术探索。
- 游戏项目与开发进度。
- 技术文章和开发日志。
- 可公开下载的数字作品。

网站不仅是传统博客，也是一处带有虚构组织氛围的个人作品基地。

中文副品牌“山嵐异造坊”表达对不同类型数字作品的创作和收集。网站在主要品牌位置优先展示英文名 `Arashi Works`，中文名作为副标题或辅助标识。

## 3. 设计主题

网站采用“幻想异造部”作为核心视觉叙事。

“异造部”不是普通企业或软件商店，而是一个持续研究、制造和收藏奇异数字造物的虚构创作组织。软件、游戏和实验项目可以被表现为异造部的项目档案、研究成果或正在进行的委托。

视觉设计应满足：

- 具有日式二次元作品的叙事感，但不直接套用常见动漫模板。
- 原创角色是品牌叙事的一部分，但不能遮挡主要内容。
- 软件和游戏信息必须保持清晰、可信和易于操作。
- 博客正文以长时间阅读体验为优先。
- 桌面端与移动端都应形成完整布局。
- 不依赖未经授权的动漫、游戏或字体素材。
- 在关闭图片或动画时，网站仍可正常浏览和使用。

## 5. 网站范围

### 5.1 首期包含

首期网站提供以下核心能力：

- 展示软件、游戏和实验程序。
- 发布技术文章、开发日志和创作记录。
- 为作品提供版本、平台、状态和下载信息。
- 支持标签、分类、归档和静态全文搜索。
- 支持匿名评论和文章阅读量。
- 提供 RSS、Sitemap 和基础 SEO。
- 适配桌面端与移动端。
- 支持亮色与暗色主题。
- 为原创角色预留完整的视觉接入能力。
- 展示山雾铃角色介绍、静态引导文案和聊天功能筹备卡片。

### 5.2 首期不包含

为控制复杂度，首期不实现：

- 用户注册和登录。
- 在线内容管理后台。
- 付费内容或付费下载。
- 私有文件和权限控制下载。
- 软件许可证、激活码或设备授权。
- 在线启动或运行软件。
- 游戏排行榜、云存档和账号系统。
- 独立动态搜索服务。
- 多语言内容系统。
- 测试版和预览版自动更新通道。
- 可实际发送消息的 AI 角色聊天。
- DeepSeek 或其他模型 API 网关。
- 聊天账号、会话同步和对话历史存储。

未来确有需求时，应重新评估这些功能，而不是在首期预留未经验证的复杂架构。

## 6. 信息架构

### 6.1 一级导航

网站采用紧凑的一级导航：

| 显示名称 | 路由 | 作用 |
|---|---|---|
| 首页 | `/` | 展示品牌、精选作品、最新手记和当前动态 |
| 作品 | `/works/` | 统一浏览软件、游戏、模组和实验项目 |
| 异造手记 | `/notes/` | 浏览技术文章、开发日志和创作记录 |
| 关于 | `/about/` | 介绍山嵐、Arashi Works 和网站信息 |
| 山雾铃 | `/about/yamagiri-rin/` | 展示山雾铃的公开角色资料 |

搜索、主题切换和其他工具作为导航栏操作按钮，不占用一级栏目。

### 6.2 作品分类

所有软件、游戏、模组和实验程序统一归入“作品”，通过类型和状态进行筛选。

作品类型：

| 类型 | 标识 | 说明 |
|---|---|---|
| 软件 | `software` | 可实际使用的桌面软件、工具和应用 |
| 游戏 | `game` | 完整游戏、开发中游戏及可玩原型 |
| 模组 | `mod` | 依赖游戏或其他宿主运行的可安装内容扩展 |
| 实验 | `experiment` | 技术验证、原型和难以归类的小程序 |

作品状态：

| 状态 | 标识 | 说明 |
|---|---|---|
| 开发中 | `in-development` | 当前仍在积极开发 |
| 已发布 | `released` | 已有可公开使用的稳定版本 |
| 维护中 | `maintained` | 主要功能稳定，仍会修复或更新 |
| 暂停 | `paused` | 暂时停止开发，但可能恢复 |
| 已归档 | `archived` | 不再维护，仅保留记录和下载 |

### 6.3 下载归属

下载不设置独立的一级入口。

每个安装包、便携版、游戏构建或相关 ZIP 均归属于一个具体作品，并在该作品详情页展示：

- 当前稳定版本。
- 支持平台和系统架构。
- 发布时间。
- 文件类型和大小。
- 下载地址。
- SHA256 校验值。
- 更新日志。
- 备用下载地址。
- 必要的安装或运行说明。

与任何作品无明确关系的文件不应默认发布。确有必要时，可在以后建立次级“资源”区域，但首期不为此增加独立栏目。

### 6.4 异造手记分类

“异造手记”统一承载博客内容，文章可以通过栏目和标签进一步组织。

建议栏目：

| 栏目 | 标识 | 内容 |
|---|---|---|
| 开发记录 | `devlog` | 软件和游戏的阶段进度、设计过程与复盘 |
| 技术笔记 | `technical` | 编程、工具、部署和问题解决记录 |
| 制作杂谈 | `making-of` | 美术、音乐、叙事、交互和创作过程 |
| 社内杂记 | `misc` | 难以归类但值得保留的短文与随笔 |

栏目用于确定文章的主要归属，每篇文章只选择一个栏目。标签用于描述语言、框架、项目名称和具体主题，每篇文章可以有多个标签。

### 6.5 辅助页面

网站还应提供：

| 页面 | 路由 | 作用 |
|---|---|---|
| 作品详情 | `/works/[slug]/` | 展示作品介绍、状态、版本和下载 |
| 手记详情 | `/notes/[slug]/` | 展示文章正文、目录、评论和阅读量 |
| 手记归档 | `/notes/archive/` | 按年份和月份浏览文章 |
| 标签总览 | `/tags/` | 展示全部内容标签并链接至筛选后的搜索结果 |
| 搜索 | `/search/` | 全文搜索作品和公开手记，并按内容类型、栏目、标签、作品类型、状态及平台组合筛选 |
| 隐私说明 | `/privacy/` | 说明评论相关数据的收集和处理 |
| 404 | `/404.html` | 引导访客返回有效内容 |

栏目与标签不建立独立详情路由，统一通过 `/search/` 的查询参数进入 Pagefind 搜索结果。搜索条件应能在刷新、复制链接及浏览器前进后退后恢复。

查询参数约定：

| 参数 | 是否可重复 | 说明 |
|---|---:|---|
| `q` | 否 | 标题、摘要和正文的搜索关键词 |
| `type` | 是 | 内容类型：`work` 或 `note` |
| `category` | 是 | 手记栏目 slug |
| `tag` | 是 | 内容标签 slug |
| `workType` | 是 | 作品类型 slug |
| `status` | 是 | 作品状态 slug |
| `platform` | 是 | 作品平台 slug |

同一筛选维度的多个值使用 OR；同一内容类型分支内的不同维度使用 AND；作品与手记分支之间使用 OR；关键词和通用条件与分支整体之间使用 AND。多值参数使用重复参数表达。

例如：

```text
/search/?q=oauth&type=note&category=technical&tag=astro&tag=tools
```
表示内容包含 `oauth`，类型为手记，栏目为技术笔记，并且标签包含 `astro` 或 `tools`。

### 6.6 首页内容顺序

首页按以下优先级组织：

1. Arashi Works 主品牌和一句简短定位。
2. 原创角色及“幻想异造部”视觉场景。
3. 精选作品。
4. 最近更新或当前开发中的作品。
5. 最新异造手记。
6. 简短的异造坊介绍。
7. 社交链接、订阅和页脚合规信息。

移动端应优先展示品牌文字和主要操作，角色插画不能把精选作品推到过深位置。

### 7.3 作品列表页

作品列表采用响应式卡片网格。

页面包含：

- 页面标题和简短介绍。
- 作品类型、状态、标签和平台的搜索入口。
- 当前公开作品数量。
- 作品卡片网格。
- 无公开作品提示。

作品列表页负责浏览全部公开作品。类型、状态、标签和平台的组合筛选统一进入 `/search/`，不在 `/works/` 中维护另一套客户端筛选逻辑。

每张作品卡片至少展示：

- 封面图或识别图。
- 作品名称。
- 简短描述。
- 作品类型。

```text

```

### 7.4 作品详情页

作品详情页包含：

- 作品名称和一句话简介。
- 封面、截图或演示媒体。
- 类型、状态、平台和更新时间。
- 主要操作按钮。
- 完整介绍。
- 功能或玩法说明。
- 当前开发状态。
- 下载与版本信息。
- 相关异造手记。
- 标签。
- 评论区。
- 相关作品推荐。

主要操作根据作品状态动态决定：

| 条件 | 主要操作 |
|---|---|
| 已有稳定公开版本 | 下载当前版本 |
| 有可玩构建但仍在开发 | 下载试玩版或体验构建 |
| 开发中且没有构建 | 阅读最新开发记录 |
| 暂停或归档 | 查看项目历史 |
| 只有在线演示 | 打开演示页面 |

按钮文字必须描述实际结果，避免只使用含义模糊的“点击这里”。

下载区应明确区分：

- 主下载地址。
- GitHub Release 等备用地址。
- Windows 架构。
- 安装版、便携版或压缩包。
- 文件大小。
- SHA256。
- 发布日期。
- 版本说明。

作品评论使用作品的规范路径作为 Waline 评论键，避免改标题或加入查询参数后生成新的评论串。

### 7.5 异造手记列表页

异造手记列表页包含：

- 页面标题和栏目说明。
- 最新文章区域。
- 指向 Pagefind 搜索结果的栏目入口。
- 指向 Pagefind 搜索结果的标签入口。
- 文章列表。
- 归档入口。
- RSS 订阅入口。

异造手记列表页不在浏览器中重复实现全文搜索或组合筛选。栏目和标签入口分别链接到：

```text
/search/?type=note&category=[category-slug]
/search/?type=note&tag=[tag-slug]
```
即使搜索脚本不可用，`/notes/` 仍展示完整的公开手记列表。

每篇文章摘要至少展示：

- 标题。
- 摘要。
- 发布日期。
- 更新日期。
- 所属栏目。
- 标签。
- 预计阅读时间。
- 关联作品（如果存在）。

首期使用静态分页，不实现依赖后端的无限滚动。

### 7.6 手记详情页

手记详情页以长时间阅读体验为优先，包含：

- 标题和摘要。
- 发布日期与更新日期。
- 栏目、标签和预计阅读时间。
- 关联作品。
- 正文。
- 桌面端文章目录。
- 阅读进度提示。
- 上一篇与下一篇。
- 相关文章。
- 评论区和公开阅读量。

正文需支持：

- 标题层级。
- 链接、列表和引用。
- 图片与图注。
- 代码块和行内代码。
- 表格。
- 提示信息块。
- 可选的脚注。
- 必要时嵌入视频或演示内容。

移动端文章目录默认折叠，不能持续占据正文宽度。

### 7.7 搜索页

搜索页使用 Pagefind 对最终静态 HTML 建立索引，统一承担全文搜索和组合筛选。

全文搜索范围包括：

- 公开作品的名称、摘要和正文。
- 公开手记的标题、摘要和正文。
- 栏目与标签的显示名称。
- 作品类型、状态、平台和功能信息。

Pagefind Filters 包含：

| Filter | 适用内容 | 值 |
|---|---|---|
| `type` | 全部 | `work`、`note` |
| `category` | 手记 | 栏目 slug |
| `tag` | 全部 | 标签 slug |
| `workType` | 作品 | 作品类型 slug |
| `status` | 作品 | 作品状态 slug |
| `platform` | 作品 | 平台 slug |

搜索状态通过 URL 查询参数保存。页面初始化时读取查询参数并恢复关键词和筛选条件；用户修改关键词或筛选控件时不立即执行搜索；点击搜索按钮或在关键词输入框中按 Enter 提交后，统一执行搜索并使用 History API 更新 URL。刷新、复制链接及浏览器前进后退应恢复已提交的搜索状态。

组合筛选采用内容类型分支模型：

- 作品分支由 `type=work` 与作品专属条件 `workType`、`status`、`platform` 组成。
- 手记分支由 `type=note` 与手记专属条件 `category` 组成。
- `tag` 是通用条件，约束所有已启用的内容类型分支。
- 同一维度的多个值使用 OR，同一分支内的不同维度使用 AND。
- 同时启用作品与手记时，两个内容类型分支之间使用 OR。
- 搜索关键词、通用条件与内容类型分支整体之间使用 AND。
- 未选择任何内容类型时，默认搜索作品与手记全部内容；此时通用条件仍然生效，作品与手记的专属条件保持休眠。
- 未选择内容类型不等同于在界面中自动勾选全部类型，表单应保持用户的实际选择状态。

整体逻辑为：

```text
关键词
AND 通用条件
AND (
    (作品 AND 作品专属条件)
    OR
    (异造手记 AND 手记专属条件)
)
```

取消某个内容类型后，其专属筛选条件保留在当前 URL 和表单状态中，但不参与搜索，作为休眠条件。重新启用该内容类型时，这些条件恢复生效。只有用户明确执行“清除筛选”时，才清除全部可见及休眠筛选条件。“清除筛选”只重置当前表单中的筛选控件，保留关键词，不立即修改 URL 或重新执行搜索；用户再次提交搜索后，才以清除后的条件更新 URL 和结果。不使用 `localStorage` 保存搜索筛选状态。

“清除筛选”只修改尚未提交的表单状态；再次提交搜索前，当前 URL 和搜索结果保持不变。

例如，只有 `tag=tools` 时搜索所有带该标签的作品与手记；只有 `category=devlog` 时栏目条件休眠，不单独触发筛选。

实现同一维度 OR 时，必须使用 Pagefind Compound Filters 的 `any`，不能直接把多个值作为数组传入，因为数组默认表示 AND。例如：

```ts
{
  filters: {
    type: "note",
    category: "technical",
    tag: {
      any: ["astro", "tools"],
    },
  },
}
```

同时启用作品和手记分支例如：

```ts
{
  filters: {
    tag: "tools",
    any: [
      {
        type: "work",
        workType: "software",
      },
      {
        type: "note",
        category: "devlog",
      },
    ],
  },
}
```

同一分支内的各维度以及通用条件默认使用 AND，维度内部通过 `any` 实现 OR；同时启用作品与手记时，使用 Compound Filters 的 `any` 组合两个内容类型分支。只有筛选而没有关键词时，调用 `pagefind.search(null, options)`。

搜索结果至少显示：

- 标题。
- 有关键词时，优先从 Pagefind 返回的页面结果及子结果中选择包含完整查询词的匹配片段，并高亮匹配内容；没有完整查询词片段时使用 Pagefind 默认匹配片段；无可用匹配片段或只有筛选条件时回退到内容摘要。
- 内容类型。
- 栏目或作品类型。
- 主要标签。
- 目标页面链接。

搜索结果应标明内容类型，避免访客混淆作品与手记。

以下内容不进入搜索索引：

- 全局导航和页脚。
- 评论内容。
- 隐私说明中的重复模板文字。
- 草稿和未公开作品。
- 纯装饰性的角色文案。

全局支持通过 `Ctrl+K` 或 `Command+K` 打开搜索，并提供可见按钮供触屏和辅助技术用户使用。搜索不可用时，不影响作品和手记页面的普通浏览。

## 8. 内容数据模型

### 8.1 总体原则

网站内容分为三类：

| 内容 | 存储形式 | 主要用途 |
|---|---|---|
| 作品 | Astro Markdown 内容集合 | 作品介绍、状态、媒体和展示信息 |
| 异造手记 | Astro Markdown 内容集合 | 技术文章、开发日志和创作记录 |
| 发布清单 | 独立 JSON | 最新版本、下载资产和软件更新检查 |

所有结构化内容均通过 Astro Content Collections 和 Schema 在构建时校验。字段缺失、枚举错误、日期无效或关联不存在时，应使构建失败，而不是生成不完整页面。

### 8.2 稳定标识

每个作品使用一个稳定的英文小写标识，同时作为作品 ID 和 URL slug。

格式要求：

- 只使用小写英文字母、数字和连字符。
- 以英文字母或数字开头和结尾。
- 发布后不随展示名称变化。
- 不复用已经归档或删除的标识。

示例：

```text
pixbox
pixel-toolkit
project-totentanz
```

对应作品地址：

```text
/works/pixbox/
/works/pixel-toolkit/
/works/project-totentanz/
```

异造手记使用独立的 slug，不要求与标题完全一致，但发布后同样应保持稳定。

### 8.3 作品内容集合

建议路径：

```text
src/content/works/
└── [id]/
    ├── index.md
    └── assets/
```

作品 Frontmatter 包含：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `title` | string | 是 | 展示名称 |
| `summary` | string | 是 | 卡片和 SEO 使用的简短介绍 |
| `type` | enum | 是 | `software`、`game`、`mod` 或 `experiment` |
| `status` | enum | 是 | 作品当前状态 |
| `publishedAt` | datetime | 条件必填 | 首次公开日期 |
| `updatedAt` | datetime | 否 | 最近有效更新日期 |
| `tags` | string[] | 是 | 用于筛选和关联 |
| `platforms` | enum[] | 是 | 支持的系统级平台：`web`、`windows`、`linux`、`android`；具体架构由发布清单表达 |
| `featured` | boolean | 否 | 是否允许进入首页精选区 |
| `draft` | boolean | 是 | 是否禁止生产构建公开 |
| `cover` | image reference | 否 | 作品封面；非草稿作品必填 |
| `screenshots` | image reference[] | 否 | 截图或演示图 |
| `repositoryUrl` | URL | 否 | 公开源代码仓库 |
| `homepageUrl` | URL | 否 | 独立主页或在线演示 |
| `releaseManifestUrl` | URL | 否 | 最新稳定版发布清单 |
| `license` | string | 否 | 软件或游戏授权说明 |
| `feedbackUrl` | URL | 否 | 正式问题反馈入口 |

作品 ID 不需要在 Frontmatter 中重复填写，由作品目录名及对应内容集合条目 ID 派生。

`cover` 和 `screenshots` 使用 Astro 内容集合的图片引用，由图片管线解析，不作为普通路径字符串处理。Schema 需要增加跨字段校验：`draft: false` 时 `cover` 必须存在；`draft: true` 时允许暂时缺少封面。公开作品缺少封面应使构建失败，而不是在生产页面使用草稿占位图。

概念示例：

```yaml
---
title: PixBox
summary: 用于整理和浏览图像素材的小型桌面工具。
type: software
status: maintained
publishedAt: "2026-01-10T12:00:00+08:00"
updatedAt: "2026-08-10T18:30:00+08:00"
tags:
  - python
  - desktop
platforms:
  - windows
featured: true
draft: false
cover: ./assets/pixbox-cover.webp
releaseManifestUrl: https://example.com/downloads/pixbox/stable.json
---
```

Frontmatter 之后的 Markdown 正文负责：

- 作品背景。
- 功能或玩法介绍。
- 使用说明。
- 开发状态。
- 已知限制。
- 截图说明。
- 其他不适合放入结构化字段的长内容。

### 8.4 作品状态规则

状态必须来自以下固定值：

```text
in-development
released
maintained
paused
archived
```

使用规则：

- `in-development`：仍在开发，可有或没有公开构建。
- `released`：已经首次公开发布，但尚未进入稳定维护阶段。
- `maintained`：功能相对稳定，继续修复和更新。
- `paused`：暂时停止开发，页面仍可公开。
- `archived`：明确停止维护，只保留历史记录。

状态与下载能力不能混为一谈。例如，开发中的游戏也可以提供试玩构建，所以页面是否显示下载按钮应取决于发布清单，而不只取决于 `status`。

### 8.5 异造手记内容集合

建议路径：

```text
src/content/notes/
└── [slug]/
    ├── index.md
    └── assets/
```

手记 Frontmatter 包含：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `title` | string | 是 | 文章标题 |
| `summary` | string | 是 | 列表和 SEO 摘要 |
| `publishedAt` | datetime | 条件必填 | 首次发布日期 |
| `updatedAt` | datetime | 否 | 实质修改日期 |
| `category` | enum | 是 | 文章主要栏目 |
| `tags` | string[] | 是 | 文章主题标签 |
| `work` | string | 否 | 关联的作品 ID |
| `draft` | boolean | 是 | 是否为草稿 |
| `cover` | image reference | 否 | 文章封面，由 Astro 图片管线解析 |
| `featured` | boolean | 否 | 是否允许首页突出展示 |
| `description` | string | 否 | 独立于摘要的 SEO 描述 |

栏目固定为：

```text
devlog
technical
making-of
misc
```

概念示例：

```yaml
---
title: PixBox 缩略图缓存的设计过程
summary: 记录桌面图像工具中缩略图缓存的实现与取舍。
publishedAt: "2026-08-10T12:00:00+08:00"
category: devlog
tags:
  - python
  - cache
  - desktop
work: pixbox
draft: false
featured: false
---
```

`work` 只保存一个作品 ID。作品详情页通过查询所有手记的 `work` 字段，自动生成相关开发日志，不在作品文件中重复维护文章列表。

与多个作品都有关的文章不强制建立多个关联，选择关系最直接的主要作品，其余关系通过标签表达。

### 8.6 草稿与发布日期

生产构建必须排除 `draft: true` 的作品和手记。

规则如下：

- 草稿可以缺少正式封面和其他非关键展示资料。
- 非草稿作品和手记必须具有有效的 `publishedAt`。
- 未来日期内容默认不公开，除非以后明确增加定时发布流程。
- `updatedAt` 只在内容发生实质变化时更新。
- 修正错别字或格式通常不需要改变 `updatedAt`。
- `publishedAt` 和 `updatedAt` 统一使用带明确时区的 ISO 8601 日期时间，例如 `"2026-08-11T01:00:00+08:00"`。
- 不使用缺少时区的本地日期时间；UTC 可以使用 `Z`，例如 `"2026-08-10T17:00:00Z"`。
- 存储精度统一到秒；页面可按场景只显示日期或显示到分钟。
- Frontmatter 中的日期时间值统一写为带引号的 YAML 字符串，避免 YAML 解析器提前转换类型。

### 8.7 标签规范

标签用于跨作品和手记聚合内容。

标签应满足：

- 使用简短、稳定且容易理解的名称。
- 相同概念不得同时存在多种大小写或拼写。
- 编程语言和框架优先使用官方名称。
- 不把作品类型、作品状态、栏目或平台重复作为标签。
- 标签显示名称与 URL slug 分离，避免中文 URL 编码影响可读性。

项目使用 `src/data/tags.ts` 集中定义标签，至少保存：

- 稳定 slug。
- 显示名称。
- 可选说明。

例如：

```text
python       -> Python
game-dev     -> 游戏开发
pixel-art    -> 像素美术
```

当前与模组项目相关的标签职责如下：

| 标签 | 显示名称 | 用途 |
|---|---|---|
| `minecraft` | Minecraft | 标识 Minecraft 游戏生态及其相关内容 |
| `utility` | 实用工具 | 标识以效率、便利性或实用功能为主要目的的内容 |

“模组”由作品类型 `mod` 表达，不重复登记同义标签。一个 Minecraft 实用模组可以使用 `type: mod`，并同时使用 `minecraft` 与 `utility` 标签。

内容文件引用标签 slug，页面显示对应名称。

### 8.8 媒体资源

作品和手记媒体分为以下几类：

| 类型 | 建议位置 | 说明 |
|---|---|---|
| 与单篇内容强关联的图片 | 内容条目附近 | 由 Astro 图片管线处理 |
| 全站共享品牌资源 | `src/assets/` | 标志、纹理和通用插图 |
| 必须保持原路径的公开文件 | `public/` | robots、favicon 等少量资源 |
| 大型视频和安装包 | 外部对象存储 | 不提交网站仓库 |

图片要求：

- 优先提供现代图片格式。
- 设置明确的宽度和高度，减少布局跳动。
- 内容图片必须具有合适的替代文本。
- 纯装饰图片使用空替代文本。
- 不在 Git 仓库中提交安装包、大型游戏构建或原始大型美术工程文件。

## 9. 发布清单与下载协议

### 9.1 权威数据来源

每个软件或游戏项目使用独立代码仓库。

各作品仓库的发布 CI 是该作品版本和下载资产的唯一权威来源，负责：

1. 运行测试和构建。
2. 生成安装包、便携版或游戏构建。
3. 计算文件大小和 SHA256。
4. 将版本化资产上传到对象存储。
5. 验证上传后的资产可访问。
6. 生成最新稳定版发布清单。
7. 最后上传 `stable.json`。
8. 创建 GitHub Release 作为发布记录和备用下载来源。

网站仓库不手工维护版本号、文件大小或 SHA256，避免网站数据与实际发布资产不一致。

### 9.2 版本规范

所有公开版本使用语义化版本 SemVer：

```text
MAJOR.MINOR.PATCH
```

例如：

```text
1.0.0
1.2.3
2.0.0
```

版本含义：

- `MAJOR`：包含不兼容变更。
- `MINOR`：增加向后兼容的功能。
- `PATCH`：向后兼容的修复。

JSON 清单中的版本不带 `v`：

```json
{
  "version": "1.2.3"
}
```

Git 标签使用 `v` 前缀：

```text
v1.2.3
```

首期只提供稳定通道，不定义 alpha、beta 或 nightly 更新协议。

### 9.3 固定清单地址

每个支持公开下载或自动更新的作品拥有固定清单地址：

```text
https://example.com/downloads/[product-id]/stable.json
```

例如：

```text
https://example.com/downloads/pixbox/stable.json
```

客户端始终请求固定地址，无需预先知道最新版本。

`example.com` 是占位域名，正式域名确定后再统一替换。

### 9.4 版本化资产地址

下载资产必须使用包含版本号的不可变地址：

```text
https://example.com/downloads/[product-id]/[filename]
```

例如：

```text
https://example.com/downloads/pixbox/pixbox-1.2.3-windows-x64-setup.exe
https://example.com/downloads/pixbox/pixbox-1.2.3-windows-x64-portable.zip
```

发布后不得覆盖同一版本路径中的文件。

如果需要修正发布资产，应提升版本号并重新发布，不能在原 URL 下静默替换文件。

### 9.5 清单结构

`stable.json` 使用带版本号的协议结构，便于未来兼容扩展。

建议格式：

```json
{
  "schemaVersion": 1,
  "productId": "pixbox",
  "channel": "stable",
  "version": "1.2.3",
  "releasedAt": "2026-08-10T12:00:00Z",
  "summary": "改进缩略图缓存并修复若干问题。",
  "releaseNotesUrl": "https://example.com/works/pixbox/#version-1-2-3",
  "assets": [
    {
      "id": "windows-x64-setup",
      "platform": "windows",
      "architecture": "x64",
      "packageType": "installer",
      "filename": "pixbox-1.2.3-windows-x64-setup.exe",
      "url": "https://example.com/downloads/pixbox/pixbox-1.2.3-windows-x64-setup.exe",
      "fallbackUrl": "https://github.com/example/pixbox/releases/download/v1.2.3/pixbox-1.2.3-windows-x64-setup.exe",
      "size": 52428800,
      "sha256": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef"
    }
  ]
}
```

字段定义：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `schemaVersion` | integer | 是 | 清单协议版本，首期固定为 `1` |
| `productId` | string | 是 | 与网站作品 ID 完全一致 |
| `channel` | enum | 是 | 首期固定为 `stable` |
| `version` | SemVer string | 是 | 不带 `v` 的稳定版本号 |
| `releasedAt` | ISO 8601 datetime | 是 | 使用 UTC 的发布时间 |
| `summary` | string | 是 | 简短版本摘要 |
| `releaseNotesUrl` | HTTPS URL | 否 | 完整更新说明 |
| `minimumOsVersion` | string | 否 | 最低操作系统版本 |
| `assets` | array | 是 | 一个或多个下载资产 |

资产字段：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---:|---|
| `id` | string | 是 | 清单内稳定且唯一的资产标识 |
| `platform` | enum | 是 | 首期固定为 `windows` |
| `architecture` | enum | 是 | `x64`、`arm64` 或实际支持的架构 |
| `packageType` | enum | 是 | `installer`、`portable` 或 `archive` |
| `filename` | string | 是 | 用户下载时看到的文件名 |
| `url` | HTTPS URL | 是 | 对象存储和 EdgeOne 主下载地址 |
| `fallbackUrl` | HTTPS URL | 否 | GitHub Release 等备用地址 |
| `size` | integer | 是 | 文件字节数 |
| `sha256` | string | 是 | 64 位小写十六进制 SHA256 |

`assets` 不得为空。每个资产的 `id`、URL 和文件名必须在同一清单内唯一。

### 9.6 JSON Schema 校验

每个作品仓库和网站仓库共享同一份发布清单 JSON Schema。

发布 CI 必须在上传 `stable.json` 前校验：

- JSON 语法有效。
- `schemaVersion` 是受支持的版本。
- `productId` 与当前仓库配置一致。
- `version` 是有效的 SemVer。
- `releasedAt` 是有效的 UTC 时间。
- `assets` 至少包含一个元素。
- 文件大小为正整数。
- SHA256 是 64 位小写十六进制字符串。
- 所有正式 URL 使用 HTTPS。
- 资产版本路径与清单版本一致。
- 主下载文件已经上传且可访问。

网站构建时再次使用同一 Schema 校验远程清单，形成第二道检查。

### 9.7 发布顺序

发布过程必须遵循“资产优先、清单最后”的顺序：

```text
创建版本标签
    ↓
运行测试和构建
    ↓
生成发布资产
    ↓
计算 size 和 SHA256
    ↓
上传版本化资产
    ↓
验证远程资产
    ↓
创建 GitHub Release 和备用资产
    ↓
生成并校验 stable.json
    ↓
最后上传 stable.json
```

这样可以避免客户端下载到指向尚不存在文件的新清单。

如果任一资产上传或验证失败，不得更新 `stable.json`。

### 9.8 网站构建取数

网站构建时根据作品 Markdown 中的 `releaseManifestUrl` 拉取远程清单。

构建流程：

1. 读取所有非草稿作品。
2. 找出具有 `releaseManifestUrl` 的作品。
3. 通过 HTTPS 下载对应清单。
4. 校验响应状态、超时、大小和 JSON Schema。
5. 确认 `productId` 与作品 ID 相同。
6. 将校验后的版本数据用于生成静态作品页面。
7. 将最终页面和其他静态资源一起部署。

浏览器默认不直接请求远程清单。访客看到的是构建时生成的静态版本信息，因此页面加载不依赖下载域名及其源站的实时状态或客户端 JavaScript。

首期远程发布清单请求超时为 10 秒，响应体上限为 256 KiB（262,144 字节）。超过任一限制均视为清单拉取失败，并使包含该公开作品的生产构建失败。

### 9.9 构建失败策略

如果任一公开作品的清单出现以下情况，生产构建必须失败：

- 网络请求超时。
- HTTP 状态不是成功状态。
- JSON 无法解析。
- Schema 校验失败。
- `productId` 不匹配。
- 清单版本无效。
- 资产列表为空。
- 正式下载 URL 不是 HTTPS。

生产部署只有在完整构建成功后才替换线上网站。构建失败时保留上一版网站，不上传半成品。

本地开发可通过明确的开发模式跳过远程请求或使用测试数据，但不能把该宽松行为带入生产构建。

### 9.10 缓存策略

建议缓存策略：

| 内容 | 缓存策略 |
|---|---|
| 版本化安装包和 ZIP | 长期缓存，并标记为不可变 |
| `stable.json` | 短期缓存，例如 5 分钟 |
| 网站中的静态版本信息 | 随网站部署更新 |
| GitHub Release 备用资产 | 由 GitHub 控制 |

版本化资产可使用：

```text
Cache-Control: public, max-age=31536000, immutable
```

`stable.json` 可使用：

```text
Cache-Control: public, max-age=300
```

发布后可以按需刷新 `stable.json` 的 EdgeOne 缓存，但不应刷新不可变版本资产。

### 9.11 客户端更新检查

支持自动更新检查的软件按以下流程工作：

1. 请求自己的固定 `stable.json`。
2. 设置合理的连接和响应超时。
3. 校验 HTTP 状态和 JSON 基本结构。
4. 确认 `productId` 与当前软件一致。
5. 使用 SemVer 比较当前版本和最新版本。
6. 根据操作系统架构选择匹配资产。
7. 向用户展示版本、摘要和文件大小。
8. 由用户确认后打开下载页或下载文件。
9. 下载完成后计算并比较 SHA256。
10. 校验失败时删除或隔离无效文件，并向用户报告错误。

网络错误、清单无效或服务不可用时，更新检查应静默失败或显示非阻塞提示，不能阻止软件正常启动。

首期使用 HTTPS 和 SHA256 保证传输安全及文件完整性，不实现发布清单数字签名。未来若威胁模型提高，再评估代码签名或 Ed25519 清单签名。

### 9.12 历史版本策略

网站详情页首期只展示最新稳定版本。

历史版本资产继续保留在版本化对象路径和 GitHub Release 中，以支持：

- 问题回滚。
- 发布审计。
- 已有链接继续有效。
- 未来增加历史版本页面。

首期不在主界面突出历史下载，避免用户误装旧版本。确需回退时，可通过 GitHub Releases 或未来的版本历史页面访问。

### 10.1 技术组成

网站采用以下工程技术：

| 层级 | 技术 | 用途 |
|---|---|---|
| 静态站点生成 | Astro | 路由、页面生成和静态构建 |
| 开发语言 | TypeScript 严格模式 | 页面逻辑、数据校验和构建脚本 |
| 内容管理 | Astro Content Collections | 管理作品和异造手记 |
| 内容格式 | Markdown | 编写作品介绍和文章 |
| 样式 | 原生 CSS | 自定义设计系统和响应式布局 |
| 浏览器交互 | 原生 TypeScript | 筛选、主题、菜单和轻量交互 |
| 搜索与组合筛选 | Pagefind CLI 与 Pagefind JavaScript API | 对构建产物建立静态索引，并按内容类型、栏目、标签和作品属性筛选 |
| 评论与阅读量 | Waline Client | 作品和手记的动态互动 |

| 端到端测试 | Playwright | 测试关键页面流程 |

| 包管理器 | npm | 管理依赖并提交 lockfile |

首期不引入 React、Vue、Svelte 或 Preact。只有在原生 TypeScript 已明显难以维护，并经过单独评估后，才考虑增加客户端 UI 框架。

### 10.2 渲染原则

网站采用 Astro 静态输出。

构建时完成：

- 生成全部公开页面。
- 过滤草稿和未来日期内容。
- 校验作品与手记 Frontmatter。
- 校验作品和手记之间的关联。
- 拉取并校验远程发布清单。
- 生成作品版本与下载信息。
- 生成 RSS、Sitemap 和 SEO 元数据。
- 运行 Pagefind 建立搜索索引。

浏览器端只承担必要交互：

- 移动端导航开关。
- 亮暗主题切换。
- Pagefind 搜索界面和组合筛选。
- 搜索查询参数与界面状态同步。
- 阅读进度。
- 按需加载 Waline。
- 少量符合视觉主题的动效。

不应把能够在构建时完成的数据处理移到浏览器端。

### 10.6 Layout 边界

Layout 负责页面共同骨架：

- `BaseLayout.astro`：HTML 文档、SEO、主题初始化、页眉和页脚。
- `WorkLayout.astro`：作品详情的标题区、内容区和相关模块。
- `NoteLayout.astro`：手记正文、目录、阅读进度和评论区域。

Layout 不负责读取所有业务数据。页面应先获取并校验数据，再将清晰的属性传给 Layout。

### 10.7 数据访问层

`src/lib/` 中集中保存可复用的数据操作，例如：

- 获取所有公开作品。
- 获取所有公开手记。
- 按日期排序。
- 根据作品 ID 查找关联手记。
- 生成标签总览所需的内容数量。
- 提供 Pagefind Filter 所需的稳定 slug 与显示名称映射。
- 读取构建期发布清单。
- 生成规范 URL。
- 生成 SEO 元数据。

页面不应各自重复实现草稿过滤、日期判断和排序规则。

数据访问函数尽量保持无浏览器依赖，以便通过 Vitest 单独测试。

### 10.8 浏览器脚本

浏览器脚本使用原生 TypeScript，并遵守渐进增强原则。

渐进增强表示：

- JavaScript 正常时提供更方便的交互。
- JavaScript 失败或被禁用时，核心内容仍可阅读和访问。

具体要求：

- 导航链接不依赖 JavaScript。
- 作品详情和下载链接不依赖 JavaScript。
- 主题切换失败时仍使用系统主题。
- Pagefind 或搜索脚本不可用时，作品列表和手记列表仍展示全部公开内容。
- 栏目和标签入口应指向规范的 `/search/` 查询参数 URL。
- 搜索条件变化应同步到 URL，并支持刷新及浏览器前进后退。
- 无效查询参数不能阻止搜索页加载。
- 搜索不可用时不影响其他页面。
- Waline 加载失败时不影响正文和下载。
- 动效脚本失败时不影响布局。

脚本只在需要的页面加载，不建立单一的全站大型客户端入口。

### 10.9 TypeScript 规则

项目启用严格 TypeScript 配置。

工程规则：

- 不默认使用 `any`。
- 外部 JSON 在运行或构建时先校验，再作为可信类型使用。
- 枚举值优先通过只读常量和联合类型表达。
- 页面属性和组件属性必须有明确类型。
- 工具函数应明确输入和返回值。
- 能够由 Astro 或 Schema 推导的类型不重复手写。
- 不使用类型断言掩盖未经校验的数据。
- 浏览器 DOM 查询必须处理元素不存在的情况。

这些原则类似于 Python 中使用类型标注与 Pydantic 校验外部数据：类型声明帮助开发，运行时 Schema 负责验证不可信输入。

### 10.10 样式架构

样式分为四层：

| 层级 | 文件 | 作用 |
|---|---|---|
| 基础重置 | `reset.css` | 统一浏览器默认样式 |
| 设计令牌 | `tokens.css` | 颜色、字体、间距、圆角、阴影和动效参数 |
| 全局规则 | `global.css` | 页面基础布局和通用元素 |
| 专项规则 | `prose.css`、`motion.css` | 正文排版与动效规范 |

组件特有样式优先放在 Astro 组件的局部 `<style>` 中。只有多个组件共同使用的规则才提升到全局样式。

不得通过大量无语义的工具类模拟完整设计系统，也不引入与自定义视觉方向冲突的通用 UI 组件库。

### 10.11 Pagefind 构建流程

Pagefind 在 Astro 构建完成后运行：

```text
Astro 生成 dist/
    ↓
Pagefind 扫描 dist/
    ↓
Pagefind 输出 dist/pagefind/
    ↓
运行静态页面与搜索冒烟测试
```

概念脚本：

```json
{
  "scripts": {
    "build:site": "astro build",
    "build:search": "pagefind --site dist",
    "build": "npm run build:site && npm run build:search"
  }
}
```

正式实施时以安装版本对应的官方命令为准，不直接假设示例脚本永远有效。

Pagefind 只扫描最终静态 HTML，从而保证搜索结果与实际上线内容一致。

作品详情页和手记详情页使用 `data-pagefind-body` 限定主要索引正文，并使用 `data-pagefind-ignore` 排除重复导航、页脚、评论容器和纯装饰内容。

结构化筛选字段通过 `data-pagefind-filter` 写入最终 HTML：

| 内容 | Filter |
|---|---|
| 作品详情 | `type:work` |
| 手记详情 | `type:note` |
| 手记栏目 | `category:[slug]` |
| 内容标签 | `tag:[slug]`，每个标签分别标记 |
| 作品类型 | `workType:[slug]` |
| 作品状态 | `status:[slug]` |
| 作品平台 | `platform:[slug]`，每个平台分别标记 |

搜索结果展示所需信息通过 `data-pagefind-meta` 提供，包括标题、摘要、内容类型、发布日期、封面地址、栏目、作品类型和标签。由于同一个 Metadata key 每页只能保存一个值，多个标签应编码为一个可安全解析的字符串，或保存为仅用于展示的标签名称字符串；不得依赖搜索结果对象自动返回页面的全部 Filter。

Pagefind Filter 保存稳定 slug，界面使用本地映射显示中文名称。不得把可能变化的中文显示名称作为筛选协议的稳定值。

### 10.12 测试结构

Vitest 负责以下单元测试：

- 草稿和未来内容过滤。
- 日期排序。
- 标签总览的公开内容计数。
- 作品与手记关联。
- SemVer 格式和比较辅助逻辑。
- 发布清单解析与校验。
- URL 规范化。
- 搜索查询参数解析和序列化。
- 重复参数的去重与无效值处理。
- 同维度 OR、分支内部 AND、内容类型分支之间 OR，以及通用条件约束全部分支的筛选转换规则。
- 内容类型关闭后，其专属条件休眠并在重新启用后恢复的规则。

Playwright 负责以下关键流程：

- 首页能够正常打开。
- 主导航在桌面端和移动端可用。
- Pagefind 可以找到测试作品和手记正文。
- 内容类型、栏目、标签和作品属性筛选可应用和清除。
- 多值筛选使用重复查询参数写入 URL。
- 刷新和浏览器前进后退可以恢复搜索状态。
- 无效查询参数不会导致页面失败。
- 作品详情能够展示正确主要操作。
- 异造手记正文和目录可用。
- 主题切换在刷新后保持。
- 键盘可以打开和关闭搜索。
- 404 页面能够返回预期内容。
- JavaScript 关闭时核心页面仍可访问。

测试使用专门的固定内容 Fixture，不依赖正式文章和远程生产清单。

### 10.13 构建阶段

完整构建流程建议为：

```text

    ↓
格式和静态检查
    ↓
Astro / TypeScript 检查
    ↓
内容 Schema 校验
    ↓
作品与手记关联校验
    ↓
发布清单拉取与校验
    ↓
Vitest 单元测试
    ↓
Astro 静态构建
    ↓
Pagefind 建立索引
    ↓
Pagefind 索引和 Filter 冒烟检查
    ↓
链接检查
    ↓
Playwright 关键流程测试
    ↓

```

CI 中不得跳过内容和发布清单校验。

### 10.14 本地开发与生产差异

本地开发需要快速启动，同时不能掩盖生产问题。

允许的开发便利：

- 使用固定 Fixture 模拟远程发布清单。
- 暂时没有正式域名时使用本地站点 URL。
- 使用测试 Waline 实例或暂不加载评论。
- 使用临时品牌图形替代最终角色素材。

生产构建必须：

- 使用真实站点 URL。
- 拉取并严格校验正式发布清单。
- 排除草稿和未来内容。
- 生成 Pagefind 索引。
- 生成正确的 canonical、RSS 和 Sitemap。
- 不包含测试数据和本地服务地址。
- 不输出密钥或环境变量内容。

开发与生产差异应由明确配置控制，不能通过散落在代码中的临时注释和手工修改实现。

## 11. 视觉设计系统

### 11.1 视觉定位

网站采用日式二次元“幻想异造部”作为视觉主题。

整体表现为一个研究、制作和收藏数字造物的虚构创作组织，融合以下视觉语言：

- 日式幻想作品的章节感和角色叙事。
- 个人开发社团的亲近感。
- 图纸、档案、部件和实验记录的造物氛围。
- 软件产品所需的清晰信息结构。
- 游戏开发所需的世界观表达空间。

网站不应直接模仿现有动漫、游戏或商业网站，也不使用未经授权的角色、图标、字体和纹理。

### 11.2 装饰密度

采用“首屏浓、正文克制”的装饰策略。

高表现区域：

- 首页首屏。
- 品牌介绍。
- 精选作品区域。
- 作品详情头部。
- 关于页面的角色介绍区域。
- 404 页面。

克制区域：

- 异造手记正文。
- 下载和文件校验信息。
- 评论表单。
- 隐私说明。
- 长列表和归档页面。
- 移动端的小尺寸操作区域。

装饰不得降低信息可读性，也不得让下载按钮、版本号和 SHA256 看起来像纯装饰文字。

### 11.3 角色接入原则

网站正式接入原创角色山雾铃，日文名为 `山霧りん`，英文名为 `Yamagiri Rin`，公开身份为“山嵐异造坊看板娘”。网站中文页面以“山雾铃”为主名称，“小铃”为昵称，角色详情页可以同时展示日文名和英文名，其他页面不重复堆叠三个名称。

角色负责：

- 引导访客认识异造坊。
- 陪伴访客浏览作品与异造手记。
- 在空状态、404 和少量提示中提供品牌化反馈。
- 展示未来角色导览聊天的筹备状态。

角色不是客服、真人工作人员或网站运行依赖。关闭角色图片、静态文案脚本或未来聊天服务后，导航、阅读、搜索和下载仍须完整可用。

角色设定资料的采用顺序：

1. v3 `01-基础三视图.png` 是身体比例、五官、发型、猫耳、尾巴、铃铛和基础颜色的权威来源。
2. v2 第 2 页只参考头部角度、表情和发型拆分。
3. v2 第 3 页参考白裙、樱花粉针织开衫、材质和服装层次。
4. v2 第 4 页参考动作、姿势及耳尾情绪反应。
5. v2 第 5 页和人格文档只选择适合公共网站的性格与习惯。

旧版资料不能覆盖新版外观。正式网页素材应根据当前设定另行绘制或导出，不直接裁切整张设定图作为立绘。

### 11.4 角色构图

桌面端首页首屏采用左侧信息、右侧角色的非对称构图：

- 品牌文字和主要按钮位于稳定的信息区域。
- 角色使用白色吊带裙与樱花粉针织开衫造型。
- 姿势优先选择轻挥手或放松站姿，视线朝向品牌和主要操作。
- 重要内容不能覆盖角色面部和关键设定细节。
- 角色也不能遮挡导航、按钮和正文。
- 背景装饰与角色保持足够层级差异。

移动端不得简单等比例缩小桌面构图，默认使用猫耳至腰部的独立裁切：

- 保留猫耳、脸部、铃铛和开衫识别区域。
- 不要求完整显示腿部和尾巴。
- 标题与按钮位置。
- 首屏总高度。
- 装饰元素数量。
- 角色是否移动到标题之后。

如果移动端空间不足，应优先保留品牌文字和主要操作，再调整角色尺寸或裁切。

关于页可以使用完整立绘。404、空状态和角色卡片使用单独半身图或表情差分，不能通过 CSS 强行放大低分辨率素材。

### 11.5 色彩策略

品牌色从角色设定发展，但界面功能色不直接照搬角色色卡。

已确认方向：

| 品牌角色 | 色彩方向 | 来源与用途 |
|---|---|---|
| 主交互色 | 深樱莓红 | 设定图标题色的加深版本，用于主要按钮、链接和选中状态 |
| 柔和强调色 | 极浅樱花粉 | 开衫与樱花，用于低对比背景和装饰 |
| 角色辅助色 | 暮紫 | 渐变发梢，用于次级强调和幻想氛围 |
| 点缀色 | 琥珀铃铛金 | 眼睛与铃铛，只用于少量高价值视觉焦点 |
| 基础表面 | 暖银白 | 发色与白裙，用于亮色主题表面层次 |
| 主要文字 | 紫调深炭色 | 与角色冷色系统协调并保持可读性 |

v3 角色参考色包括 `#F0EAEA`、`#D0C6F3`、`#E1A13A`、`#F6E4D6`、`#F8C4B5`、`#E6E6EA`、`#D8A947` 和 `#FBFBFB`。这些值用于校对角色素材，不自动成为按钮、正文或状态颜色。

设计系统定义以下语义令牌，最终数值在视觉原型和对比度测试后锁定：

| 令牌类别 | 用途 |
|---|---|
| `background` | 页面主背景 |
| `surface` | 卡片和内容区域 |
| `surface-raised` | 浮层、菜单和重点卡片 |
| `text-primary` | 主要文字 |
| `text-secondary` | 辅助说明 |
| `text-muted` | 弱化元数据 |
| `border` | 普通边界 |
| `border-strong` | 强调边界 |
| `accent` | 主要品牌强调色 |
| `accent-hover` | 强调色交互状态 |
| `accent-soft` | 大面积浅强调背景 |
| `success` | 成功、可用和已发布状态 |
| `warning` | 警告、暂停和注意事项 |
| `danger` | 错误及破坏性提示 |
| `focus` | 键盘焦点轮廓 |
| `character-purple` | 角色暮紫辅助色 |
| `character-gold` | 铃铛金点缀色 |

颜色必须满足：

- 普通正文与背景对比度至少达到 WCAG AA。
- 大号文字和图标也需要满足适用的对比度要求。
- 下载、错误和状态不能只靠颜色表达。
- 亮暗主题中的同一语义保持一致。
- 角色代表色不能直接替代所有功能色。
- 大面积高饱和色仅用于必要的视觉焦点。

### 11.6 主题策略

网站提供亮色和暗色主题。

首次访问时跟随系统的 `prefers-color-scheme` 设置。用户主动选择后，将选择保存在浏览器本地，并在后续访问中优先使用。

主题初始化应尽早执行，避免页面加载后明显闪烁。

规则如下：

- 没有 JavaScript 时仍能跟随系统主题。
- 本地存储不可用时不影响页面浏览。
- 主题按钮具有可理解的文本或无障碍名称。
- 亮暗主题均需单独检查角色素材和装饰元素。
- 图片不应通过简单反相来适配暗色主题。
- 代码块、表格、评论区和搜索界面均需支持两种主题。

### 11.7 字体策略

中文正文使用可靠的系统字体栈，避免下载体积巨大的中文 Web Font。

概念字体栈：

```css
font-family:
  "Microsoft YaHei",
  "PingFang SC",
  "Noto Sans CJK SC",
  system-ui,
  sans-serif;
```

正式实现时应根据 Windows、macOS、Android 和 iOS 的实际表现调整顺序。

英文品牌标题首选开源字体 `Cormorant Garamond`，以 WOFF2 格式自托管，用于 `Arashi Works`、英文展示标题和极少量章节编号。

品牌字体要求：

- 支持英文大小写、数字和常用标点。
- 允许网站嵌入和自托管。
- 文件体积合理。
- 字形优雅、具有高对比衬线和幻想叙事感，但仍容易阅读。
- 不用于长篇中文正文。
- 加载失败时具有接近的系统回退字体。

正文、界面和代码分别采用不同字体角色：

| 用途 | 字体方向 |
|---|---|
| 英文品牌和大型标题 | 品牌西文字体 |
| 中文正文和界面 | 系统无衬线字体 |
| 代码、版本号和 SHA256 | 等宽字体 |

不得使用难以辨认的装饰字体展示下载信息、版本号和正文。

字体授权文件随自托管字体一并保留。不得依赖 Google Fonts 等在中国大陆可能不稳定的第三方字体服务。

### 11.8 字体层级

建议使用有限且稳定的字体层级：

| 层级 | 用途 |
|---|---|
| Display | 首页品牌和大型章节标题 |
| Heading 1 | 页面主标题 |
| Heading 2 | 页面主要分区 |
| Heading 3 | 内容子分区 |
| Body | 正文和界面说明 |
| Small | 日期、标签和辅助信息 |
| Code | 代码、版本号和校验值 |

字号使用响应式范围而不是为每个设备编写大量固定值。

大型标题可使用 `clamp()`，但上下限必须经过移动端和超宽屏验证。

正文要求：

- 中文正文行高约为 `1.7` 至 `1.9`。
- 正文行宽控制在约 60 至 75 个英文字符的视觉范围。
- 移动端保留足够左右边距。
- 段落间距由样式统一控制，不在 Markdown 中插入空白字符。
- 长 URL、文件名和 SHA256 可以安全换行或横向滚动。

### 11.9 图形语言

界面装饰可以从以下元素发展：

- 风和山岚的流线。
- 图纸网格与测量标记。
- 档案编号和项目标签。
- 机械零件或魔导装置轮廓。
- 星芒、符号和研究印记。
- 作品状态章。
- 类似活动记录的日期标记。
- 猫耳三角轮廓与铃铛圆形结构。
- 从开衫针织纹理抽象出的低对比线条。

这些元素应统一抽象程度，避免同时混用不相关的：

- 赛博朋克 HUD。
- 中世纪羊皮卷。
- 现代企业仪表盘。
- 像素游戏窗口。
- 玻璃拟态组件。

如果后续角色设定明确包含某种世界观语言，再统一调整图形系统。

品牌徽记以“猫耳与铃铛”为核心。完整标志可以加入极少量风环或樱瓣，但 favicon 应只保留猫耳轮廓和铃铛主体，确保在 16×16 像素时仍可辨认。角色头像不直接作为 favicon，徽记也不能完全替代 `Arashi Works` 文字品牌。

### 11.10 卡片设计

作品卡片是网站的重要识别组件。

卡片应包含：

- 明确的封面区域。
- 作品类型标识。
- 作品名称。
- 简短摘要。
- 状态和更新时间。
- 少量主要标签。
- 清晰的进入详情提示。

卡片视觉可以带有“异造档案”或“研究项目”的暗示，但不能成为传统后台面板。

交互要求：

- 悬停时使用轻微位移、边界或阴影变化。
- 键盘焦点效果不得弱于鼠标悬停。
- 触屏设备不依赖悬停显示必要信息。
- 卡片高度不强制完全相同，但网格节奏应稳定。
- 封面缺失的草稿和测试内容使用明确占位图形。
- 状态和类型使用文字配合图形，不只使用颜色。

### 11.11 正文设计

异造手记正文区域应弱化世界观装饰，让内容成为视觉焦点。

正文设计要求：

- 背景安静，不使用影响阅读的高对比纹理。
- 标题层级清楚。
- 链接有明确下划线或其他非颜色提示。
- 引用块与普通正文容易区分。
- 代码块支持横向滚动和复制操作。
- 表格在移动端可以安全横向滚动。
- 图片和图注保持明确关联。
- 提示块区分信息、警告和错误，但不滥用。
- 目录和阅读进度属于辅助功能，不能抢占正文注意力。

角色可以出现在文章页的页头、页尾或少量提示元素中，不应持续固定在正文旁边制造视觉干扰。

### 11.12 下载区域设计

下载区域以可信和清晰为第一目标。

必须突出：

- 当前版本。
- 文件类型。
- 支持平台与架构。
- 文件大小。
- 发布时间。
- 主下载操作。
- SHA256 校验值。
- 备用下载入口。

下载按钮不能伪装成广告，也不能在同一区域放置多个视觉权重相同但含义不明的按钮。

SHA256 使用等宽字体，并提供适合复制的布局。校验值过长时允许换行，但不能截断实际内容。

### 11.13 动效原则

动效用于表达层级和增强幻想氛围，而不是持续吸引注意力。

允许的动效：

- 页面进入时的轻微淡入和位移。
- 卡片悬停和焦点反馈。
- 导航菜单展开与收起。
- 主题切换的短暂过渡。
- 筛选结果变化。
- 阅读进度。
- 首屏少量风纹、粒子或图纸元素运动。
- 角色素材允许时的轻微分层视差。
- 铃铛或樱瓣在状态变化时的一次性轻动效。

避免：

- 大面积持续漂浮。
- 长时间自动播放的复杂背景。
- 干扰阅读的闪烁。
- 强烈缩放或旋转。
- 滚动劫持。
- 为装饰引入大型动画运行库。
- 每个元素依次出现导致页面等待过久。

### 11.14 动效呈现策略

网站动效作为视觉体验的一部分，应保持完整呈现，不根据 `prefers-reduced-motion` 自动关闭或削弱。

动效仍应遵循以下限制：

- 不使用滚动劫持。
- 不让动效阻碍导航、阅读或主要操作。
- 不使用持续时间过长的入场动画。
- 循环装饰动效不得明显干扰正文。
- 动效不得导致内容隐藏或交互状态不明确。
- 优先使用 `transform` 和 `opacity`，避免引起频繁布局计算。

### 11.15 响应式断点原则

断点根据布局失效的位置确定，不围绕具体设备型号设计。

重点验证：

- 窄屏手机。
- 普通手机。
- 平板和小型笔记本。
- 常规桌面显示器。
- 超宽桌面窗口。

移动端规则：

- 导航转为可访问的折叠菜单。

## 14. 未来 AI 角色聊天安全架构

### 14.1 首期边界

首期只展示角色卡片和“异造坊导览对话正在筹备”说明：

```text
角色卡片
  ├── 山雾铃简介
  ├── 聊天功能筹备状态
  └── 不发送任何聊天网络请求
```

卡片不伪装成可用输入框，不放置失效的发送按钮，不申请通知权限，不创建空会话，也不加载 DeepSeek SDK。

### 14.2 未来目标架构

正式启用前必须新增独立服务：

```text
浏览器
    ↓ HTTPS
独立聊天网关
    ├── 请求和来源校验
    ├── IP、会话与设备限流
    ├── 会话上下文管理
    ├── 输入输出内容审核
    ├── Token、并发与预算控制
    └── 脱敏日志与告警
    ↓
DeepSeek API
```

浏览器只访问自有网关。DeepSeek API Key 只保存在服务端环境变量或密钥服务中，任何构建产物、网页源代码、响应和日志均不得包含 Key。

### 14.3 网关安全要求

网关必须：

- 固定允许使用的模型和上游 API 地址。
- 在服务端注入独立安全版 System Prompt。
- 拒绝客户端传入 System Prompt、模型名、上游地址和任意代理参数。
- 校验请求方法、内容类型、消息结构和字段长度。
- 限制单次输入、输出 Token、历史消息数和上下文总长度。
- 设置请求超时、并发上限和流式输出最长持续时间。
- 按 IP、会话和设备等维度实施速率限制。
- 设置每小时、每日和每月预算阈值及硬熔断。
- 对异常请求量、错误率和成本增长告警。
- 提供不依赖重新部署的一键关闭开关。
- 对输入和输出执行适合公共网站及未成年角色形象的内容安全策略。
- 对日志做脱敏，默认不保存完整私密对话。

CORS、`Origin`、`Referer`、CSRF 防护和验证码可以提高滥用成本，但不能替代身份、配额和服务端限流。隐藏接口地址或在前端加入固定签名不构成可靠保护。

### 14.4 明确禁止

- 把 DeepSeek Key 放在 Astro 前端或任何 `PUBLIC_` 环境变量。
- 暴露通用 OpenAI 兼容反向代理接口。
- 允许调用者选择任意模型或转发任意请求体。
- 将完整原始人格文档发送给浏览器。
- 接受无限历史消息或无限输出。
- 把完整聊天内容写入普通访问日志、分析平台或错误上报。
- 让聊天服务故障影响静态网站、作品下载或评论功能。

### 14.5 上线门槛

未来聊天只有同时满足以下条件才可开放：

- 完成单独威胁模型审查。
- 确认用户身份策略和公开配额。
- 限流、并发、Token 和预算熔断通过测试。
- 隐私说明明确数据用途、保存期限与删除方式。
- 完成提示词注入、越权参数和内容安全测试。
- 验证关闭开关及上游故障降级。
- 完成成本压测并设置云平台及 DeepSeek 双重告警。

### 15.2 资源边界

| 资源 | 用途 | 访问权限 |
|---|---|---|
| 网站 COS 桶 | HTML、CSS、JavaScript、图片、字体和搜索索引 | 通过 EdgeOne 公开读取 |

### 15.3 COS 与 EdgeOne 规则

- 禁止公共目录列表。
- 网站桶配置静态站点与 404 页面。
- 下载桶支持 Range 请求和断点续传。
- 对象使用正确 `Content-Type`；下载资产设置合理的 `Content-Disposition`。
- 版本化资产路径不可变，发布后不覆盖。
- 同一站点按内容路径配置缓存规则；`/downloads/*` 另行区分发布清单与版本化资产。
- 全站强制 HTTPS，根域与 `www` 使用单一规范地址。
- 开启流量、带宽、请求量和费用告警。

缓存建议：

| 内容 | 缓存策略 |
|---|---|
| HTML | `no-cache` 或短缓存 |
| 内容哈希 CSS、JavaScript、字体 | 一年并标记 `immutable` |
| 版本化图片 | 30 天至一年 |
| 版本化下载资产 | 一年并标记 `immutable` |
| `stable.json` | 5 分钟并支持 ETag |

使用 EdgeOne 中国大陆可用区、腾讯云 COS 和大陆服务器域名之前，先确认 ICP 备案及腾讯云接入备案状态。正式上线后按所在地要求办理公安联网备案，并在页脚展示有效链接和备案号。

备案未完成时只进行本地开发或明确的临时预览，不把临时海外部署视为中国大陆正式可用性方案。

## 17. 安全、隐私与合规

### 17.1 静态网站与 EdgeOne

- 全站 HTTPS。
- 确认全部子域支持 HTTPS 后再评估 HSTS `includeSubDomains`。
- 设置与 Astro、Pagefind、Waline 及实际资源匹配的 CSP。
- 设置 `X-Content-Type-Options: nosniff`。
- 设置合理的 `Referrer-Policy` 和 `Permissions-Policy`。
- 外部新窗口链接使用 `rel="noopener noreferrer"`。
- 不加载来源不明的统计、字体和第三方脚本。

### 17.2 Waline

- Waline 固定明确版本，不长期使用不可控的 `latest`。
- 服务只监听回环地址或容器内部网络。
- 公网仅开放 HTTPS 和受限管理入口。
- 新评论默认审核后公开。
- 邮箱不公开展示。
- 配置安全域名、频率限制、重复内容检查和请求体大小限制。
- 管理账号使用强密码，JWT Token 使用强随机值。
- SQLite 和备份不得放在 Web 根目录。

### 17.3 隐私说明

隐私页至少说明：

- Waline 处理的昵称、邮箱、IP、评论内容和必要技术信息。
- 信息用于评论展示、审核、通知、安全和反垃圾。
- 邮箱默认不公开。
- 数据保存位置和大致期限。
- 用户申请删除评论和相关数据的方式。
- 第三方资源与外部链接的边界。
- 未来聊天启用前需另行补充对话数据说明。

### 17.4 内容与版权

- 网站代码、文章、软件、下载资产和角色素材分别声明许可或版权。
- 山雾铃的角色设定、立绘、差分和徽记均由山嵐原创并保留版权，不因网站代码公开而采用网站代码的开源许可证。
- 允许对山雾铃的角色素材进行非商业分享和非商业二次创作，使用时须署名“山嵐”并注明原始来源；未经另行授权不得用于商业用途。
- 不发布无合法分发权的字体、图片、音乐、安装包或游戏资产。
- 角色素材源文件和网页导出文件均记录作者及版权归属。

| 角色美术无损源文件 | 独立受控存储并另做离线备份 |
| 版本化下载资产 | COS，重要版本另做归档 |
| Waline SQLite | 每日一致性备份到私有 COS |
| 云配置 | 部署文档记录，可自动化部分使用脚本或 IaC |

Waline 备份建议保留最近 7 个每日、4 个每周和 6 个每月版本。每月至少执行一次测试恢复，不以“备份任务成功”代替恢复验证。

### 18.4 成本边界

当前低流量目标仍按每月约 20 至 50 元规划，不含域名续费和未来 AI 聊天费用。购买前必须复核腾讯云当期价格、续费价格、EdgeOne、COS、HTTPS 请求和出网计费。

未来 DeepSeek 聊天预算独立计算，不与网站基础费用混合。聊天功能必须具有硬预算熔断，不能只依赖余额提醒。

## 19. 测试与验收

### 19.1 内容与构建

- 无效 Frontmatter、关联或发布清单使构建失败。
- 草稿和未来内容不进入页面、RSS、Sitemap 和搜索。
- 非草稿作品没有 `cover` 时构建失败。
- 图片引用可以由 Astro 图片管线解析。
- 远程清单失败不会替换上一版线上网站。

### 19.2 页面与交互

- 首页、作品、异造手记、关于、隐私和 404 页面可访问。
- 桌面和移动布局无页面级横向滚动。
- 亮暗主题可用且首次加载无明显闪烁。
- 键盘可完成导航、搜索、筛选、主题切换和评论区核心操作。
- `prefers-reduced-motion` 下关闭非必要动画。
- JavaScript 关闭时仍可阅读、导航和下载。

### 19.3 角色与视觉

- v3 权威外观特征在正式立绘中保持一致。
- 桌面和移动构图均不遮挡标题、按钮和导航。
- 猫耳、脸部和铃铛不被意外裁切。
- 静态角色文案只出现在对应情境，且不进入搜索索引。
- 不出现禁止公开的人格内容。
- 聊天筹备卡片明确不可用，不产生网络请求。
- 角色素材不会导致明显布局跳动或不合理首屏体积。

### 19.4 搜索、评论与下载

- Pagefind 能搜索中文作品名称、摘要与正文。
- Pagefind 能搜索中文手记标题、摘要与正文。
- 内容类型、栏目、标签、作品类型、状态和平台 Filter 正确。
- 同一维度多值使用 OR，同一内容类型分支内不同维度使用 AND，作品与手记分支之间使用 OR，关键词和通用条件约束全部分支。
- 已关闭内容类型的专属条件保留在 URL 中但不参与搜索，重新启用后恢复生效。
- 搜索条件可通过 URL 分享，并在刷新和浏览器前进后退后恢复。
- 未选择内容类型时，关键词和通用标签默认作用于作品与手记全部内容，内容类型专属条件保持休眠。
- 草稿、未来内容、全局导航、页脚、评论和纯装饰文案不进入索引。
- Pagefind 加载失败时，作品和手记的普通浏览仍可使用。
- 评论默认审核，邮箱不公开，服务失败不影响正文。
- Waline 使用规范路径作为评论与阅读量键。
- 下载资产 URL、文件大小和 SHA256 与清单一致。
- 下载失败时备用入口和校验信息仍清楚可见。

### 19.5 部署验收

- PR 无法读取生产凭证。
- 失败部署保留上一版网站。
- 并发部署不会让旧提交覆盖新提交。
- 网站、评论、清单和下载均使用 HTTPS。
- COS、EdgeOne 和 CAM 符合最小权限与缓存规则。
- Waline 备份可恢复到测试实例。

未来聊天启用时另增网关专项验收，不把首期“筹备中”卡片视为聊天功能验收完成。

## 22. 方案结论

Arashi Works 首期建设为以 Astro 静态输出为核心的品牌作品站：作品、异造手记、搜索、角色视觉和下载信息在构建期生成；Waline 独立承担评论和公开阅读量；版本化软件资产由各作品仓库发布到 COS 并通过静态清单接入网站。

山雾铃作为山嵐异造坊看板娘参与首页、关于页、404、空状态和静态引导文案，但不成为核心功能依赖。首期聊天只显示筹备卡片，不连接 DeepSeek 或任何模型 API。未来聊天必须通过独立受控网关，并在身份、限流、内容安全、隐私和硬预算熔断全部通过专项验收后再开放。
